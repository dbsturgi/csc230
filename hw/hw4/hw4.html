NC State Park Search

For this homework assignment, we’ll be developing a program that lets users search for state parks or other locations of interest in North Carolina. It’s called parksearch. The following shows how a user might interact with the program. The text that’s in bold shows what the user types. The rest is output from the program.

When we run the program, we use command-line arguments to give it the names of files containing lists of cities and parks. The two files shown here are examples given with the starter. The cities-c.txt file contains a list of 10 cities in North Carolina, and parks-c.txt contains information about 10 state parks and recreation areas.

After starting, the program prompts the user for a query. First, the user asks for a list of all the cities. The program echos the user query then prints out a list of the cities read at program start-up, each with latitude and longitude.

After listing all the parks, the user asks for a list of at most 5 parks, each one with a list of park features. Then, the user asks for a list of parks that have swimming among their features, reporting each one with its GPS coordinates.

Finally, the user user requests a list of parks that have camping, sorted by their distance to Raleigh each reported with their distance to Raleigh. The user enters this last query twice, with the options given in a different order. At the end, the user signals the end-of-file on standard input by pressing ctrl-d. This causes the program to terminate.

City and Park Lists

During execution, the parksearch program maintains a city list and a park list. The city list is a list of cities, each with a name and global coordinates stored as latitude and longitude. For each park, the park list stores a name, global coordinates and a list of features for the park. These lists are used to let the user select parks that offer the features they’re interested in.

Program Execution

FR-1 : The city list and park list can be populated based on city files and park files read at program start-up.

The parksearch program expects two types of filenames on the command line, city files and park files. The name of a city file must start with the string “cities-”. These files contain a list of cities in a format described below. The name of a park file must start with the string “parks-”; these files contains lists of parks. The program can be run with any number of park and city files given on the command line. It can even be run with no filenames, but then the city and park lists will be empty.

If the program is run with invalid command-line arguments, it should print a line with the following usage message to standard error and terminate with an exit status of EXIT_FAILURE.

usage: parksearch [ parks-file.txt | cities-file.txt ]*

If the program can’t open one of the given files for reading, it should print the following message to standard error and exit with a status of EXIT_FAILURE. Here, filename is the name of the file given on the command line. The program should report the first filename on the command line that it can’t successfully open (i.e., if there are multiple filenames on the command line that can’t be opened, it just needs to report this error for the first one that can’t be opened).

Can't open file: filename

Park File Format

Like the example shown below, a park file contains zero or more records for parks. Each park record starts with a name of 1 to 40 characters. The name may include spaces, so an entire input line is used for the name; it extends from the start of the line up to the last character before the newline.

The park name is followed by GPS coordinates, given as floating point values for latitude and longitude. This is followed by an integer, n and then n strings giving features of the park. Each park can have between zero and 10 features and each feature is a string of 1 to 15 non-whitespace characters.

Other than the park name, fields describing the park can be separated by any amount of whitespace. The first line of a park file must be the name of the first park, and the name of each subsequent park must start on the next line after the last feature of the previous park, or after the number of features, n, if the previous park has zero features.

User Queries

FR-2 : The user can enter queries to see the contents of the city list or the park list.

After the parksearch program starts, the user will be able to enter queries to see a list of cities or to search through the park list. Before each query, the program will prompt the user with the following string. This string has one space at the end, right after the > character.

cmd>

After the user enters a query, the program will echo it back to the user. This just means that the program will print a copy of the query the user just entered before printing the response to the query. Echoing a copy of the query like this will help when we’re capturing program output in a file. It gives us a way to capture a copy of each user query, right before the program’s response to the query.

If the user enters an empty line, the program will echo it (a blank line) then prompt again for another user input. Input lines that consist of only whitespace aren’t considered errors; they’re just ignored by the program.

All queries start with the word cities or parks. The parks query can be followed by additional options to let the user select particular parks or report different information about the selected parks. There can be additional whitespace at the start or end of the user input or between the options for a parks query.

User queries can be up to 100 characters long. If an input line is longer than 100 characters, the program will read and discard any additional characters on the line after the first 100. It will echo the first 100 characters of the input line, followed by the string ‘…’ to indicate that there was additional input that was discarded. A line longer than 100 characters is considered an invalid command, so an interaction with the program could look like:

cmd> This is a long query.  The program won't even get a chance to parse it since it won't store the whole input line.
This is a long query.  The program won't even get a chance to parse it since it won't store the whol...
Invalid command

Cities Query

FR-2.1 : The user can enter a cities query to get a report of all the cities on the city list.

If the user enters cities, the program should print a report of all the cities in the format shown below. Cities should be sorted lexicographically by their names. Each line of output should give the city name, left-justified in a 20-character field. This should be followed by a space, then the city latitude right justified in an 8-character field. This should be followed by another space and then the city longitude right justified in an 8-character field. The latitude and longitude values should be rounded to three fractional digits.

Apex                   35.733  -78.850
ChapelHill             35.913  -79.056
Hendersonville         35.319  -82.461
HighPoint              35.956  -80.005
Wilmington             34.236  -77.946

If the city list is empty, the program should print a line with the following message to standard output and then prompt for another command.

City list empty

Parks Query

FR-2.2 : The user can enter a parks query to get a report of parks on the park list.

If the user enters parks, the program should print a report of parks in the park list. The basic parks report is just a list of park names, sorted lexicographically by name. Each park name should be printed left-justified in a 40-character field. This means that there will typically be some spaces at the end of each output line, so every output line is exactly 40 characters in length. The spaces at the end of each line will help with options that report additional information about each park. Extra output columns added to the right will still line up.

Grandfather Mountain State Park         
Hanging Rock State Park                 
Kerr Lake State Recreation Area         
Pilot Mountain State Park

The parks query can be followed by several optional parameters, each one consisting of two values. Optional parameters can be given in any order after the word parks.

Parks limit Option

FR-2.3 : The output for a parks query can be limited to a user-specified number of parks.

The parks query can be followed by the word, limit, and then a positive integer, m. This limits the number of parks printed to just the first m. For example, the following query would report at most 5 parks. If there are fewer than 5 parks on the park list or if other parameters are used to select parks, it could print fewer than 5.

cmd> parks limit 5

The input is considered invalid if the value after the word, limit can’t be parsed as a positive integer.

Parks with Option

FR-2.4 : The output for a parks query can be specialized to report only parks with a user-selected feature.

The parks query can be followed by the word, with, and then a string of 1 to 15 non-whitespace characters, f. This causes the query to report only those parks that have the feature, f, in their feature list. To match, the park must have a feature that matches the given string exactly, including capitalization. For example, the following would list only those parks that had “swimming” on their feature list.

cmd> parks with swimming

The with option is considered invalid if it isn’t followed by a word, or if the word is longer than 15 characters. It’s not considered an error if the user asks for a feature that’s not available at any park.

Parks near Option

FR-2.5 : The output for a parks query can be ordered by distance to a city.

The parks query can be followed by the word, near, and then the name of a city, c, from the city list. If this option is provided, the parks in the output will be ordered by their distance to the given city. Parks that tie for distance (unlikely) should be ordered by name. Distance will be approximated based on the global coordinates of the park and city and 3958.8 as the approximate radius of the earth, in Miles. For example, the following query will order cities based on their distance to Raleigh.

cmd> parks near Raleigh

The near option is considered invalid if it isn’t followed by a word, or if the word isn’t the name of a city on the city list. The given name must match the name of a city on the city list exactly, including capitalization.

Parks show Options

FR-2.6 : The output for a parks query can be configured to include global coordinates of each park, the list of features for each park or the distance to a selected city when the near option is used.

The parks query can be followed by the word, show and then either the the word location, features or distance. If show location is specified, then each park name in the listing will be followed by global coordinates for that park. Global coordinates will be added to each line as a space, then the latitude of the park, right aligned in an 8-column field, then another space then the longitude in an 8-column field. Latitude and longitude values will be rounded to three fractional digits of precision. With this option, output of a parks query could look like:

Grandfather Mountain State Park            36.111  -81.812
Hanging Rock State Park                    36.412  -80.254
Kerr Lake State Recreation Area            36.441  -78.369
Pilot Mountain State Park                  36.341  -80.463

If show features is specified, then each park name in the listing will be followed by the list of features for that park. Features for each park will be listed in the same order they occurred in the parks input file. Features will be separated by a single space, with a space at the start to separate them from the park name. With this option, output of a parks query could look like:

Grandfather Mountain State Park          birdwatching camping hiking
Hanging Rock State Park                  biking camping
Kerr Lake State Recreation Area          birdwatching fishing hiking paddling
Pilot Mountain State Park                horse-riding picnicking rock-climbing

The show distance option requires that the near c option be included elsewhere in the query. With this option, the parks report will include the distance of each park to the given city, c. The distance report will start with a space, then the distance to the city (in miles), right aligned in an 8-column field rounded to two fractional digits. With the show distance option, output of a parks query might look like:

parks near HighPoint show distance
Hanging Rock State Park                     34.43
Pilot Mountain State Park                   36.90
Kerr Lake State Recreation Area             97.19
Grandfather Mountain State Park            101.56

The show option is invalid if it isn’t followed by location, features or distance. The show distance option is only valid if a near option is given in elsewhere in the query (either before or after the show option).

Invalid Commands

FR-3 : For invalid user inputs, the program will print an “Invalid command” message, ignore the command and prompt the user for another command.

A query is considered invalid if:

  • It’s longer than 100 characters
  • It doesn’t start with cities or parks
  • A cities keyword is followed by non-whitespace characters.
  • A parks keyword is followed by something that doesn’t match one of the valid options described above.
  • The same option is given more than once for a parks query. For example, a query can’t give the limit option more than once, even if it has the same limit value, m. If you do the extra credit described below, you can permit more than one with option and more than one show option.

If the user enters an invalid command, the program will echo the command (or the first 100 characters of it if it’s too long), then print a line saying “Invalid command” to standard output. Then, the program will prompt the user for another input.

Program Termination

FR-4 : The program should terminate when it reaches the end-of-file on standard input.

After the user is done entering queries, they can type ctrl-d to signal the end-of-file on standard input. If the program is reading input redirected from a file, it will just terminate when it reaches the end-of-file.

Extra Credit

This assignment includes a couple of additional requirements that you can implement for extra credit. Implementing each of these extra credit features is worth five extra credit points. If you implement both of them, that’s worth 10 points of extra credit.

FR-2.7 : A parks query may include multiple with options. If more than one with options is given, then the output should list parks that have all of the requested features.

If you implement FR-2.7, then your parksearch program will be able to search for parks that have a set of features, not just a single, selected feature. Although this requirements permits multiple with options, a query with multiple with options for the same feature would still be considered invalid.

FR-2.8 : A parks query may include multiple show options.

If you implement FR-2.8, then your parksearch program can report multiple, optional output fields. Each of the show options can be given in the query, and the output will include the optional output fields in the same order they are specified in the query. Each of the optional output fields can be given at most once, and show distance can only be given if the query also includes a near option.

Feature lists for each park may be different lengths; some parks may have more features or longer names for their features. So, for FR-2.8, if show features is given before show distance or show location, then the output for park location and distance probably won’t line up as a column. That’s OK. You’re not expected to make the output for show features take the same amount of space for all parks.

Design

The following sections describe how your program should work and some of the functions you will need to implement and use.

Program Organization

Your implementation will be organized into four components. The coords component defines a structure for representing global coordinates and computing approximate distance between two locations on the surface of the earth. The parklist and citylist components will contain code for parsing, storing and managing the park list and city list. The parksearch component is the top-level component, containing main() and code to parse and execute user queries.

The following figure shows the organization of these components. The parksearch component uses code from the other three components. The citylist and parklist components don’t directly interact with each other, but they both use the coords component help store city and park locations and to compute distances.

Since the coords, parklist, and citylist components provide functions that are used elsewhere in the program, they will each have a header file that prototypes these functions. These headers will also define types (e.g., structs) used elsewhere in the program. The top-level component won’t need a header, since there aren’t any other components that use the functions it defines.

Struct Type Names

This assignment depends on using typedef to map structure names to short type names. For example, typedef is used to map the structure for a park to the type name, Park. This lets us use shorter type names, without having to give the struct keyword over and over when we’re talking about these types.

Global Coordinates

The starter for this assignment includes a complete implementation of the coords component. It defines a struct, Coords, for representing global coordinates as latitude and longitude, and it provides a function, globalDistance() for computing the approximate distance between any two locations on the surface of the earth.

City and CityList Representation

This assignment is a good chance to get some experience using structs, dynamic memory allocation and resizable arrays. Each city will be represented by a struct, City, with a character array for its name and an instance of the Coords struct for its global coordinates.

The city list will be implemented as an instance of the CityList struct. It will contain fields for implementing a resizable array of City instances. The list field is a pointer to a dynamically allocated array of City instances, capacity records the size of the array, and count is the number of cities currently stored in the array. When a CityList is first created, it will allocate an array of City structs with a a capacity of 5. As cities are read from the input, it may need to enlarge this array, doubling its size whenever it runs out of space.

You can add more fields to the City and CityList structs, but don’t change or remove the existing fields. The unit test program depends on these fields for some of its tests.

Park and ParkList Representation

Each park will be represented by an instance of the Park struct. It contains an array of characters for storing the park name, an instance of Coords for storing the park location, a 2D array, flist, for storing the list of park features and an integer fcount the number of features the park has.

The park list will be represented with a dynamically allocated instance of the ParkList struct. It will contain fields for implementing a resizable array of pointers to Park instances. Notice that this is different from the CityList. Here, the array is an array of pointers, with the Park instances stored elsewhere in memory. With the City list, the array contained all the City instances, so no additional heap memory was needed to store each city. Here, you’ll need to allocate space for the array of pointers, then another block of memory for each City instance one of these pointers points to. Your resizable array of pointers should start with an initial capacity of 5, and it should double in capacity whenever the array needs to be enlarged.

You can add more fields to the Park and ParkList structs, but don’t change or remove the existing fields provided with the starter. The unit test program uses some of these fields to help test your code.

Expected Functions

As part of your implementation, you will define and use the following functions. You can define more if you want to. Just try to put them in a component that’s suitable for whatever they do and remember to mark them as static where you can. A function that’s intended to be used by other components should be non-static, and it should have a prototype and a block comment in the header file for that component. A function that’s for internal use by just one component should be defined and marked static in that component; its block comment should be right before the definition of the function.

Your citylist component should have the following five functions.

  • CityList *makeCityList()
    This function dynamically allocates storage for the CityList, initializes its fields and returns a pointer to the new CityList. It’s kind of like a constructor in Java.

  • void freeCityList( CityList *cityList )
    This function frees the memory used to store the given CityList, including the array of City structs and the CityList itself.

  • void readCities( CityList *cityList, char const *filename )
    This function reads all the cities from a city file with the given filename. For each city, it fills in one of the City structs in the list array, growing it as needed.

  • void listCities( CityList *cityList, FILE *fp )
    This function prints all the cities in the format described above, sending output to the given file. Of course, the caller can provide stdin as the file pointer to get this function to print to the terminal.

  • bool locateCity( CityList *cityList, char const *name, Coords *loc )
    This function looks for a city with the given name in the city list. If the city is found, it returns true and puts the city’s global coordinates in the given Coords struct. If the city can’t be found, the function returns false.

Your parklist component should have the following five functions.

  • ParkList *makeParkList()
    This function dynamically allocates storage for the ParkList, initializes its fields for a resizable array of pointers to Park instances and returns a pointer to the new ParkList. It’s like a constructor in Java.

  • void freeParkList( ParkList *parkList)
    This function frees the memory used to store the given ParkList, including freeing space for all the Park instances, freeing the array of pointers to Parks and freeing space for the ParkList struct itself.

  • void readParks( ParkList *parkList, char const *filename )
    This function reads all the parks from a park file with the given filename. For each park in the input, it allocates an instance the Park struct and stores a pointer to it in the resizable array, growing the array when needed.

  • void sortParks( ParkList *parkList, int (*comparator)(void const *, void const * ) )
    This function sorts the parks in the given parkList. It uses the qsort() function together with the function pointer parameter to order the parks. The function pointer is described in the “Sorting Parks and Cities” section below.

  • void listParks( ParkList *parkList, FILE *fp, bool (*selector)( Park * ), void (*customizer)( Park *, FILE * ), int limit )
    This function prints parks from the park list. The limit parameter lets the caller specify a limit on the number of parks that should be printed. The limit parameter should be a non-negative value indicating the maximum number of parks to report. If limit is zero, the function should print arbitrarily many parks. The selector and customizer functions are for choosing what parks to print and for adding additional output to the report for each park. These are described in more detail below in the “Selecting Parks” and “Customizing Park Output” sections.

Your top-level, parksearch.c file will contain the main() function. You’ll also implement and use the following two functions to help organize and simplify your solution:

  • static int getLine( char line[], int limit )
    This function is for reading lines of user input from the terminal. It stores the text of each line in the line array. The limit parameter tell the function the length of the line array, so it won’t buffer overflow. The function will always read a whole line of text, but it will have to discard characters if the input line is too long. The function should return EOF is there are no more lines to be read from standard input. It should return 1 (true) if the next line is read successfully, and it should return 0 (false) if the input line was too long and some of it had to be discarded. Use this function to read input from the user. Reading a whole input line at once will make it easy to parse the command in the handleCommand() function below, or to discard the whole line if it’s invalid.

  • static bool handleCommand( char const *cmd )
    This function is for parsing and responding to a user query, stored in the cmd string. You can use functions like sscanf() to parse parts of the command and then call functions in the citylist or parklist components to perform the requested action. The function should return true or false to indicate whether the given command is valid.

Global Variables

In general, you should avoid using global variables in your program. It makes it more difficult to reuse code and it can create conflicts in the global namespace.

In the starter code, the top-level parksearch.c component uses two static global variables to keep up with the park list and city list. It’ OK for you to use these two variables. You will also need to use some additional global variables to implement the near and with options. It’s OK to use global variables to support these features, but you shouldn’t need globals for other parts of the program.

Parsing User Queries

With help from the getLine() function, it will be easy to read user input one line at a time. After reading a line of input, you can use sscanf() to parse the type of query and query options.

Remember, unlike reading from a file, sscanf() doesn’t automatically resume parsing from where it left off on the last call. For example, you couldn’t call something like sscanf( str, "%d", &x ); to read an int then call sscanf( str, "%d", &y ); again to read the next int. If you gave sscanf() the same string in two successive calls, it would just start parsing at the start of the string each time. If you want to parse multiple values out of the same string, you can do it all at once, like sscanf( str, "%d%d", &x, &y );, or you could advance the pointer on successive calls to sscanf(), as in sscanf( str + offset, "%d", &y );. We talked about this near the middle of lecture 11.

Sorting Parks and Cities

Cities in the input could be in an arbitrary order, but your program will need to report them in sorted order in response to a cities query. You should use the standard library qsort() to perform the sorting for you, but you’ll need to give it a pointer comparator function to get it to order the cities by name. Remember that you give qsort() a pointer to the start of the array you want to sort, it computes the addresses of elements of the array and passes those to your comparator function as void pointers. For the CityList, the array contains instances of City, so you will want to convert these void pointers to pointers to City, so you can get access to the cities fields.

For sorting parks, the sortParks() lets client code order the park list using any comparison function that’s needed. Use this to get the list of parks the right order before printing it with listParks(). The array inside ParkList is an array of pointers to Park instances, so a pointer to an array element will be a pointer to a pointer to a Park. When qsort() calls the comparator function, it will provide two pointers to array elements as void pointers. You will need to convert these to pointers to pointers to Park in order to get to the fields of a park for that element.

For sorting parks, you’ll need two comparator functions, one that orders parks by name and one that orders by distance. For the latter, you will need some way for the comparator to know the location of the reference city given with the near command. You can use a static global variable for this. Inside the comparator function, you can check the distance between the reference city and each of the given parks and return a value to indicate how the two parks compare. For example, if the first parameter to the comparator is closer to the city, your comparator should return a negative value.

Selecting Parks

The listParks() function expects a pointer to a selector function. Use this to decide which parks to print. Given a pointer to a Park, this function returns true if that park should be printed. If you want to print every park, you can pass in a pointer to a function that always returns true. If you want to print just those parks with a particular feature, you can pass in a pointer to a function that looks for a specified feature on each park’s flist. Inside the selector function, you’ll need to know what feature to look for. You can use a static global variable for that. If you find the with option while parsing a query, you can save the requested feature in this global variable, then, inside your selector function, you can check this global variable to see what feature you should be looking for.

Customizing Park Output

The show option lets the user select additional output to report while listing parks. The customizer parameter for listParks() is used to add additional output while writing the parks report. After printing the name of each park, listParks() will call this function to give it the opportunity to add some output to the end of each line. For example, if you want to report the location of each park, you can pass in a pointer to a function that will print the latitude and longitude of a park. For reporting park features, you can use a pointer to a different customizer function. For reporting distance, you’ll need another customizer function. To compute distance, this last customizer function can use the same global variable used when sorting parks by distance to the reference city.

Function Visibility

Any functions that are needed by a different component should be prototyped and commented in the header. Functions that are intended for internal use within a component should not be prototyped in the header. A function for internal use should be commented in the implementation file, and should be marked static (given internal linkage), so it won’t be visible to any other part of the program. This is like making the function an implementation detail of its component, something we could change if we wanted without affecting other parts of the program.

The comparator, selector and customizer functions are examples of functions that can be static. You’ll define them in the top-level, parksearch.c. Although they are called by a different component, they’re not actually called by name; they’re called using a function pointer. The linker won’t be responsible for hooking up the calls to these functions with their definitions. For the comparator, selector and customizer functions, we’re writing code to do that ourselves by passing function pointers to code that needs to use the function.

Output Alignment

Normally, printf will right-align output values in a given field width. You can use a negative value for the field width to get it to left align instead.

Build Automation

You get to implement your own Makefile for this assignment (called Makefile with a capital ‘M’, no filename extension). Its default target should build your program, compiling each source file to an object file and then linking the objects together into an executable.

As usual, your Makefile should correctly describe the program’s dependencies, so targets can be rebuilt selectively, based on what source files have changed. It should also have a clean rule, to let the user easily delete any temporary files or target files that can be rebuilt the next time make or the system test script is run (e.g., the object files, the executable and any temporary output files).

In addition to the “-Wall” and “-std=c99” options that we normally include when we’re compiling, be sure to include the “-g” flag. This will be useful when you try to use gdb or valgrind to help debug the program. Since you’ll be using a constant for PI, you’ll need to use the -D_GNU_SOURCE when you compile a source file. Memory Errors and Leaks

On any test that runs successfully, your program is expected to free all of the heap memory it allocates and close any files it opens. Although it’s not part of an automated test, we encourage you to try out your executable with valgrind. We certainly will when we’re grading your work. Any leaked memory, use of uninitialized memory, access to memory outside the range of an allocated block or leaked files will cost you some points. Valgrind, which is discussed in lecture 16, can help you find these errors before we do.

Your program is not expected to free memory or close all its files on error tests, those tests where your program is supposed to exit unsuccessfully. On these test cases, your program may need to exit from inside some function, where you don’t have access to all the memory you’ve allocated or all the files you’ve opened. In these cases, your program can just exit right away, without having to free all resources.

The compile instructions above include the -g flag when building your program. This will help valgrind give more useful reports of where it sees errors. To get valgrind to check for memory errors, including memory leaks, you can run your program like the following. This example runs the program on the first test case. You can use similar commands to try your program on any test case using valgrind.

$  valgrind --leak-check=full --show-leak-kinds=all --track-fds=yes ./parksearch cities-a.txt < input-01.txt
... lots of output ...

If you want to run valgrind, you have to run it on each test case individually. You can’t run the test script inside valgrind (well, you can, but then you will be getting valgrind output for the shell, rather than for the program you wrote). Sometimes students try to run something like “valgrind test.sh”. Just be aware that this won’t work.
